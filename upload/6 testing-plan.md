# ПЛАН ТЕСТИРОВАНИЯ (TEST PLAN) – NARRATIVECORE

## Версия 1.0 – MVP и основные сценарии

---

## 1. ОБЪЕКТ ТЕСТИРОВАНИЯ

Веб-приложение NarrativeCore (MVP), включающее:
- Бэкенд API (NestJS)
- Фронтенд (React + FSD)
- Базу данных PostgreSQL
- Redis (очереди, кэш)
- S3-хранилище (MinIO в тестах)
- AI-воркер (OpenAI API вызывается, но для регресса может использоваться заглушка)

---

## 2. УРОВНИ ТЕСТИРОВАНИЯ

| Уровень | Инструменты | Кто проводит |
|---------|-------------|--------------|
| Модульное (Unit) | Jest (бэк), Vitest (фронт) | Разработчик |
| Интеграционное | Supertest (API бэка), React Testing Library | Разработчик / QA |
| E2E | Playwright / Cypress | QA |
| Нагрузочное | k6 | DevOps / QA |
| Приёмочное (UAT) | ручное тестирование + бета-тестеры | QA + писатели |

---

## 3. ОБЛАСТЬ ТЕСТИРОВАНИЯ (MVP)

### 3.1. Функциональные модули

- Регистрация, логин, просмотр профиля.
- Управление проектами (CRUD).
- Управление сущностями (6 предустановленных типов + пользовательские типы).
- Динамические поля.
- Связи между сущностями.
- Редактор глав (создание, редактирование, удаление, порядок).
- Контекстная панель (распознавание сущностей в тексте).
- Проверка канона (подсветка конфликтов, панель проблем).
- AI-генерация (сущность, сцена, иллюстрация) – с квотами.
- Визуальный граф (отображение, навигация).
- Версионирование (авто-бэкапы, ручные версии, восстановление).
- Экспорт (JSON, Markdown, HTML-вики).
- Тарифные ограничения (Free/Pro).

### 3.2. Нефункциональные тесты

- Производительность API (время ответа < 500 мс для CRUD).
- Нагрузка на очередь BullMQ (одновременные запросы генерации).
- Безопасность (JWT, защита от XSS, CSRF, SQL-инъекции – статический анализ + ручная проверка).
- Совместимость браузеров (Chrome, Firefox, Safari последние версии).

### 3.3. Что НЕ тестируется в MVP

- Коллаборация (будет в 2.0).
- Семантическая проверка канона (будет в 2.0).
- Мобильная версия.
- Экспорт в EPUB, PDF, Twine.
- Импорт из внешних систем.

## 4. КЛЮЧЕВЫЕ ТЕСТ-КЕЙСЫ (E2E)

### 4.1. Регистрация и логин

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| A1 | Регистрация с валидным email и паролем | Создаётся пользователь с тарифом free, возвращается токен |
| A2 | Регистрация с существующим email | Ошибка 400 |
| A3 | Логин с верными данными | Токен выдаётся |
| A4 | Логин с неверным паролем | Ошибка 401 |

### 4.2. Проекты и сущности

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| B1 | Создание проекта с именем | Проект отображается в списке |
| B2 | Создание персонажа (поля: имя, описание, статус, фракция) | Сущность сохраняется, отображается в каталоге |
| B3 | Добавление динамического поля «возраст: 25» | Поле сохраняется и отображается в карточке |
| B4 | Создание связи «враг» между двумя персонажами | Связь видна в карточках и в графе |
| B5 | Удаление сущности, на которую есть связи | Связи удаляются каскадно, ошибок нет |

### 4.3. Редактор глав и контекст

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| C1 | Создание главы, ввод текста «Хохотунья пошла в доки» | Контекстная панель показывает сущности «Хохотунья» и, возможно, «доки» (если локация создана) |
| C2 | Изменение порядка глав (drag‑and‑drop) | Порядок меняется, при обновлении страницы сохраняется |
| C3 | Выделение текста «Создать сущность» | Появляется модальное окно с предзаполненным именем, после сохранения сущность появляется в каталоге |

### 4.4. Проверка канона

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| D1 | В каталоге персонаж «Хохотунья» статус «alive», в главе написано «Хохотунья погибла» | Жёлтая подсветка при наведении показывает конфликт |
| D2 | В главе упоминается «Неизвестный», такой сущности нет | Красная подсветка, в контекстной панели статус missing |
| D3 | Нажатие кнопки «Проверить канон» | Панель проблем показывает список конфликтов с фрагментами текста |

### 4.5. AI-генерация

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| E1 | Генерация персонажа с промптом «хитрый торговец» | Возвращается карточка с заполненными полями (принимаем/редактируем) |
| E2 | Генерация сцены «диалог между Хохотуньей и агентом» | Текст вставляется в редактор, учитывает карточки сущностей |
| E3 | Генерация иллюстрации для выделенного абзаца | Через 5–30 секунд появляется изображение, вставляется в главу |
| E4 | Попытка генерации на бесплатном тарифе | Ошибка 402 или кнопка неактивна |

### 4.6. Граф

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| F1 | Открыть граф проекта | Все сущности и связи отображаются в виде узлов и рёбер |
| F2 | Перетащить узел, увеличить масштаб | Позиция сохраняется в локальном хранилище, при перезагрузке – возвращается (или по умолчанию) |
| F3 | Двойной клик по узлу | Открывается карточка сущности |

### 4.7. Экспорт

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| G1 | Экспорт в JSON | Файл скачивается, содержит все сущности, связи, главы, метаданные |
| G2 | Экспорт в Markdown | Файл содержит все главы в порядке следования и глоссарий в конце |
| G3 | Экспорт в HTML-вики | Архив .zip, при распаковке index.html открывается, навигация работает |

### 4.8. Версионирование

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| H1 | Автоматическое сохранение версии при изменении проекта | В списке версий появляется новая запись с меткой Auto |
| H2 | Ручное сохранение версии с комментарием | Версия сохраняется с указанным комментарием |
| H3 | Восстановление старой версии | Проект возвращается к состоянию на момент версии (главы, сущности) |

## 5. ТЕСТОВАЯ СРЕДА

- **Dev-среда:** `dev.narrativecore.app` (после каждого коммита автоматически деплоится из ветки develop)
- **Staging:** `staging.narrativecore.app` (перед релизом на прод)
- **Production:** `app.narrativecore.app`

**Данные для тестирования:**
- Предустановленный тестовый пользователь с тарифом pro (для проверки квот)
- Пустой проект «Тестовый мир» + предсозданные 5 сущностей (персонажи, локации)

---

## 6. АВТОМАТИЗАЦИЯ ТЕСТОВ

### 6.1. Модульные тесты (бэкенд)

Охват: не менее 70% для критических модулей (auth, entities, chapters, canon, ai).  
Пример: каждый сервис должен иметь тесты на основные методы CRUD и проверку конфликтов.

**Команда запуска:** `pnpm test:unit` (в монорепозитории)

### 6.2. Интеграционные тесты API

Использовать `@nestjs/testing` + `supertest`.  
Тестировать эндпоинты с реальной БД (тестовая Postgres в Docker).

**Обязательные тесты:**  
- Регистрация/логин  
- Создание проекта и проверка прав  
- Создание сущности с dynamic_fields  
- Создание связи  
- Проверка канона (на искусственном тексте)

### 6.3. E2E (Playwright)

Основные сценарии:  
1. Регистрация → создание проекта → добавление персонажа → написание главы → проверка канона  
2. Генерация сцены → вставка → сохранение → экспорт

Запуск в CI при pull request в main.

### 6.4. Нагрузочное тестирование (k6)

Сценарии:  
- 100 параллельных пользователей создают сущности  
- 50 пользователей одновременно экспортируют в Markdown  
- 20 пользователей генерируют сцены (с очередью)

Ожидаемое поведение: время ответа не выше 500 мс для CRUD и 2 с для экспорта; очередь не переполняется.

## 7. ПРИЁМОЧНОЕ ТЕСТИРОВАНИЕ (UAT)

Пригласить 5–10 писателей (из целевой аудитории) на закрытый бета-тест.  
Выдать список задач (checklist) и форму обратной связи.

**Критерии успешного UAT:**  
- 90% задач выполнены без критических ошибок.  
- Средняя оценка удобства интерфейса ≥ 4 из 5.  
- Нет блокеров (приложение не падает, данные не теряются).
